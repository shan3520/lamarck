# Real repositories, free models (runs 2–8, 2026-10-03 to 10-17)

**Question:** does harness evolution help a coding agent on *real* repository tasks, not just the toy benchmark?

**Short answer:** not shown, and the most promising signal did not hold up. No run shipped a change. In run 8 (a roomier agent, 26 calibrated tasks), an edit gained +7.8 pts on train and +5.0 pts on 10 never-seen tasks, inside the noise band. A **pre-registered confirmation** with 12 rollouts per task reversed it: **−7.5 pts** (full-pass 49.2% → 41.7%, noise 5.4 pts). The safeguards did their job every time, and nothing was shipped on noise. On real repositories with free models, harness evolution has not yet produced an improvement that generalizes.

## Setup common to all runs
- **Tasks:** mined from git history (`mine-git`) and checked SWE-bench style (`validate-tasks`: tests fail before the real fix, pass after it).
  - Runs 2–5: 13 tasks from itsdangerous and python-slugify (8 train / 5 held-out).
  - Runs 6–7: a pool of 74 tasks (itsdangerous 9, python-slugify 5, more-itertools 60), calibrated down to 11.
- **Agent:** Lamarck's mini bash agent; its instruction file `AGENT.md` is the harness being evolved.
- **Proposer:** `openai/gpt-oss-120b` on Groq's free tier, in every run.
- **Cost:** $0 throughout (free tiers only).

## Run 7 in detail
- **Accepted on train:** round 2's process edit: a rule to re-run the tests after every code change and finish only when they pass, plus an "iterative test verification" skill. It was confirmed at g = +0.75 task units against a noise floor of 0.73, i.e. just barely.
- **Rejected afterwards:** rounds 3–6 tried "edit exactly where the traceback points" variants.
  - Three lost on screening (g = −1.00, −1.50, −0.50).
  - One was blocked by the critic for mentioning `ValueError`. That was a false positive: Python built-in names are now exempt.
- **Held-out (5 never-seen tasks × 4 rollouts each, per harness):**

  | | Seed | Evolved |
  |---|---|---|
  | Full passes | 3 / 20 | 2 / 20 |
  | Rollouts that hit the 25-step limit | 17 / 20 | 18 / 20 |
  | Tokens per rollout | 38k | 50k (+31%) |

- **Reading it:** the held-out difference is one rollout, well inside the noise. The edit made the agent spend more without solving more, so the train gain was most likely a lucky draw that just cleared the floor. Most held-out rollouts ran out of steps under either harness: these tasks need more steps or a stronger model, not just better instructions.
- **The gate did its job:** a borderline in-loop gain was stopped before it shipped.

## Run 8 in detail
- **Why a new agent configuration:** probes on 10 tasks Nemotron had never solved showed that the mini agent's defaults, not the model, were the main limit.

  | Probe (same 10 Nemotron walls) | Tasks solved at least once |
  |---|---|
  | DeepSeek V4.1 Flash, default agent (25 steps, 4-step memory, 1,500-char observations) | 1 / 10 |
  | DeepSeek V4.1 Flash, roomy agent | 9 / 9 reached |
  | Nemotron, default agent | 0 / 10 |
  | Nemotron, roomy agent | 3 / 10 |

  DeepSeek's free allowance on Token Harbor ran out after 17 roomy rollouts (about 137k tokens each), so the run used Nemotron (free on NVIDIA).
- **Calibration** of the 74-task pool with roomy Nemotron found 14 learnable tasks, 17 solved and 43 walls. Re-checking the 17 "solved" tasks with 4 rollouts showed 12 of them fail sometimes, which gave 26 learnable tasks (16 train / 10 held-out).
- **Search:**
  - Rounds 1–4 proposed the same idea four times: check that the code still imports after each edit, phrased as general advice. All lost on screening (g = −0.25, −0.25, −0.75, −2.25).
  - Round 5 made it concrete and was confirmed at g = +1.25 against a noise floor of 1.06, with R = 0.50. The rule: *"After any code edit, immediately run `python -c "import more_itertools"`; if it fails, revert or fix before proceeding."*
  - Round 6 passed screening and failed the re-test (g = +1.00 ≤ floor 1.03).
- **Held-out (10 never-seen tasks × 4 rollouts each, per harness):**

  | | Seed | Evolved |
  |---|---|---|
  | Full passes | 18 / 40 (45%) | 20 / 40 (50%) |
  | Tokens per rollout | 109k | 114k (+5%) |

  - **8 of 10 tasks scored identically** under both harnesses, including the itsdangerous and python-slugify tasks. The repo-specific import check did not hurt the other libraries.
  - The gain comes almost entirely from one task (1/4 → 4/4), partly offset by another (3/4 → 2/4). That is why it does not clear the noise band.
- **Reading it:** the first real-repo edit whose gain survives to never-seen tasks with the right sign, at low cost. It is not yet distinguishable from luck. The rule is repo-specific rather than task-specific: it names the package that 22 of 26 tasks share. That is the kind of house knowledge Lamarck is meant to learn for a team's repo, but a suite spanning several repos should check that such a rule applies to each repo it is used on.
- **Proposer repetition, measured:** rounds 1–5 all pursued one theme, verifying the code after each edit. It looked like wasted repetition, which cost about 120 rollouts, so a critic rule rejecting near-duplicates of rejected proposals was planned. Measured on the actual edits, the four rejected versions share only 25–30% of their words with each other, and the accepted round-5 edit shares just as much with them. A duplicate filter strict enough to stop the repeats would also have stopped the success. The repetition was refinement: vague advice failed until it became one concrete command. The planned filter was dropped.
- **Infrastructure lessons, now fixed:**
  - The PC idle-slept for hours. `run` and `calibrate` now keep it awake.
  - The connection dropped every ~20 minutes, which killed long attempts. The network retry budget is now per outage.
  - A shutdown could cut off a save mid-write. Resume now tolerates it.
  - `calibrate` now waits out outages (`--wait`).

## Run 8 confirmation (pre-registered)
- **Why:** run 8's held-out gain (+5.0 pts) sat inside its noise band (9.3 pts). Re-testing until something passes would be p-hacking. So `lamarck confirm` ran **one** pre-registered re-test, and its plan was pushed before any rollout finished ([plan](2026-10-17-run8-confirmation-plan.json)).
- **Design:** the same 10 held-out tasks; the seed harness and the evolved harness; 8 new rollouts each with seeds the run never used (10004–10011), pooled with the run's 4. SHIP only if the gain exceeds the combined bootstrap noise band.
- **Result: DO NOT SHIP. The direction reversed.**

  | | Seed | Evolved |
  |---|---|---|
  | Full passes (12 rollouts × 10 tasks) | 59 / 120 (49.2%) | 50 / 120 (41.7%) |
  | Rollouts that hit the 50-step limit | 53 / 120 | 67 / 120 |
  | Tokens per rollout | 108k | 117k (+8%) |

  - **The loss is broad:** 6 of 10 tasks got worse, including python-slugify (11/12 → 8/12).
  - **The mechanism is visible:** the rule's import check after every edit spends steps from a fixed budget, so more rollouts run out of steps before finishing.
  - Run 8's +5.0 pts on 4 rollouts per task was luck. Its own gate already refused to ship it, and the confirmation shows why that caution matters.

## What went wrong, and what changed

### 1. Most real tasks were walls (fixed: `lamarck calibrate`)
In runs 2–5 the agent solved 0–1 of 8 train tasks at all. When every harness scores 0 on a task, that task carries no signal, so no edit could show a gain. Calibrating the 74-task pool with Nemotron found:

| Zone | Tasks |
|---|---|
| Wall (never solved in 2 tries) | 60 |
| Already solved | 3 |
| **Learnable** | **11** |

Only 15% of validated real tasks were usable. With calibration, run 6 started at 29.2%, with 5 of 6 train tasks in the variance zone, against 0–1 of 8 before. Calibration rollouts use their own seeds and are never reused by the run, because tasks are selected on them.

### 2. The proposer fixated on one bug (fixed: critic plus prompt)
In runs 2, 3 and 5, nearly every proposal was a "timestamp handling" skill for one itsdangerous commit: domain knowledge for a single task, not a reusable behavior. Two changes:
- The critic now rejects code identifiers (e.g. `SignatureExpired`, `date_signed`) that appear in only one task.
- The proposer is told to fix the agent's *process*.

In run 6, every proposal was a process fix: "re-run the tests after every edit and loop until they pass".

### 3. The cost rule didn't scale (fixed: per-success cost rule)
In run 6, round 2's candidate showed the largest gain of any real-repo candidate on screening: g = +1.25 tasks, about +21 pts. It was rejected before its re-test as "too expensive", because it made the agent spend 25% more tokens running tests. The absolute rule (4,000 tokens per task of gain) was calibrated on toy rollouts of about 1.5k tokens, while real-repo rollouts cost about 35k.

The new default: a candidate may add tokens only if **tokens per solved task don't rise**. Applied to run 6's numbers, it admits that candidate to re-testing and still rejects the three weak, expensive ones (g = +0.25 at +16% to +31% tokens).

### 4. Free-tier engineering problems (fixed, but they contaminated earlier runs)
- **Run 5 is confounded.** Nemotron with thinking on spent its whole per-step budget on hidden reasoning and often returned nothing, at about 1 minute per step. With thinking off, a step takes about 1 s, and calibration solved a task Nemotron had failed 8 of 8 times in run 5.
- **Gemini** filtered about 9 of 12 agent replies as "malformed function calls" until the agent was given a native `bash` tool. Run 3 was restarted from scratch after the fix.
- **Network outages:** 5 rollouts in run 2 recorded an internet outage as task failures. They were removed, and outages now pause the run. One overnight outage in run 6 cost about 4 hours.
- **Quotas and throttles:**
  - Groq's rolling daily token limit made run 2 take about 5 days.
  - NVIDIA's bare `429` throttles were mislabelled as daily quota.

  Both are now handled by waiting inside the attempt.

### Mid-run changes, disclosed
- **Run 2:**
  - the failure miner's clustering changed after round 1;
  - 5 network-failure rollouts were removed;
  - the agent's quota-wait setting was raised (infrastructure only).
- **Run 7:** the cost rule was changed after seeing run 6's *train-side* decisions. Run 6's held-out tasks were never evaluated, so run 7's held-out verdict is still on never-seen data. Run 7 replays run 6's rollouts where the computation is identical (seed evaluation and round 1).

## The remaining hard limit: statistical power
With 6 train tasks × 4 rollouts, the noise floor in run 6 was 0.76 task units, about 13 pts. A real but modest improvement (+5 to +10 pts) cannot be distinguished from luck at this size. To detect smaller gains Lamarck needs one of these:
- **more learnable tasks**, from more repositories or from a stronger agent (a stronger model turns walls into learnable tasks);
- **more rollouts per task**, at higher cost.

Free models plus small Python libraries give about 11 learnable tasks, which is enough to catch only large effects.

## What this does and doesn't show
- **Shows:** the safeguards behave as designed on real repositories:
  - nothing shipped on noise;
  - task-specific edits were blocked;
  - the held-out set stayed untouched.

  It also shows that calibration is essential, and that a frozen weak model on real repos leaves little room for instruction-level improvement.
- **Doesn't show:** that harness evolution improves real coding agents. The honest next test needs a stronger agent (e.g. Claude Code as the target), so far more tasks are learnable and a 5–10 pt gain is measurable.

## Fixed after run 7 (not used in any run above)
- The critic no longer treats Python built-in names (`ValueError`, `NameError`...) as task-specific.
- Saved task files keep repository paths relative to the file.
